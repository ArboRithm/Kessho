Sync the memory ​

This journey keeps the memory up to date across your machines, with git: see where the repository stands, sync, commit your changes, resolve a conflict. The application does it in one click; the agent does it with four tools, with safeguards.

What you ask the agent ​

You ask your agent

« Where does my memory's Git synchronization stand? Query the remote first. »

→ The agent callsmem_git_status
  • fetch = true
You ask your agent

« Synchronize my memory with the remote. »

→ The agent callsmem_git_sync
You ask your agent

« Commit my changes with the message "session notes" and push. »

→ The agent callsmem_git_commit
  • message = session notes
You ask your agent

« There is a conflict with the remote: show me the three versions of each file. »

→ The agent callsmem_git_resolve

Syncing is not automatic: the agent calls mem_git_sync when you ask ("sync the memory", "where is git at?") or when it judges it useful. The delivered procedures (see Connect the agent) invite it to do so at the start of a session, with the resume, and at the end of a session, with the archive; an agent that does not follow them will not do it on its own.

What the agent does ​

  1. mem_git_status returns the repository state: branch, remote (without credentials), ahead and behind, uncommitted changes, operation in progress, files carrying conflict markers, state of the Obsidian Git plugin. It writes nothing and uses no network by default; fetch: true queries the remote first. If git is not found, the state says so with the installation command, and the agent relays it to you without running it.

  2. mem_git_sync (no parameters) fetches, rebases your local commits if the remote moved, then pushes. Never forced, never an automatic stash. A real conflict aborts the rebase: the repository goes back to its previous state, no marker is left, and the files involved are returned. It is refused if uncommitted changes prevent the rebase.

  3. mem_git_commit commits the uncommitted changes (paths for only some, otherwise all) with message (non-empty, 1,000 characters at most), then pushes (push: false to skip). It is to be called only with the user's explicit agreement: those changes are yours. It refuses a file that carries conflict markers, unless allow_markers: true for a file that merely quotes them.

  4. mem_git_resolve resolves a real conflict, in two steps:

    • without resolutions, it inspects: for each file in conflict it returns its three versions (base, local, distant) and an empreinte, then aborts: the repository does not change;
    • with resolutions (the resolved text of each file, or keep: "local" or "distant") and the empreinte returned (handed back in fingerprint), it redoes the merge, writes the texts, commits and pushes. If the repository or the remote moved in between, nothing is done; no marker is ever accepted or left.

    The catalog asks for it to be used only with the user's agreement on the merged text.

What the agent does not do ​

  • Initializing the repository and connecting a remote are gestures of the application (Settings › Sync): no tool does them.
  • It never forces a push and never commits your changes on its own initiative.

The automation on every write ​

When the memory is a git repository and the Automation box ("Agents commit and sync automatically") is ticked, every agent tool that writes is wrapped: before writing it checks the remote, after writing it commits what it touched, and only that, then pushes. Your uncommitted changes do not leave with it, except a file you had already modified and that the tool rewrites: that one leaves with the commit, which names it (a Kessho-Embarque line), and the agent must tell you. Read tools do not run git; mem_git_sync, mem_git_commit and mem_git_resolve sit outside this wrapping because they are the gesture themselves.

The result of a writing tool then carries a sync report, which the agent reads every time:

statutWhat it meansWhat the agent does
synchroniseCommitted and pushed.Nothing.
commite_localCommitted here, not pushed (offline, no remote, authentication refused…).Tells you in one line, with the reason.

What you see ​

The application shows the same repository, and it is the one that does in one click what mem_git_sync does through the agent: the Sync the memory button in the status bar commits, pulls, then pushes. The GIT field says where the repository stands (up to date, N to push, N to pull, conflict…), and Settings › Sync carries the Sync, Pull and Push actions, the Commit message, the remote and the Automation box. Everything is described in Sync.

One difference worth knowing: the button commits everything that changed under an automatic message ("vault backup: …"), whereas the agent only commits your changes with your agreement.
